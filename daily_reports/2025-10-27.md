### 3. SVG Border Rendering Consistency Fix

**Status**: Completed
**Commit**: `ce4e9b8` (17:48 on 10/28, but part of this work session)
**Files Modified**:

- `src/components/map/CaliforniaMapSimple.tsx`

**Problem Identified**:

Selected counties showed inconsistent border thickness - some edges appeared bold while others appeared thin, especially where counties share boundaries. This was due to SVG stroke rendering behavior where adjacent paths overlap.

**Root Cause Analysis**:

- SVG strokes render centered on the path edge by default
- When two adjacent counties both have strokes, they overlap
- The overlapping portion can appear thinner due to rendering order
- Vector scaling can cause stroke width inconsistencies at different zoom levels

**Changes Made**:

```typescript
// Increased stroke width for better visibility
strokeWidth: isHovered || isDragging ? 6 : 1  // Previously 4

// Added SVG rendering attributes
style={{
  paintOrder: 'fill stroke',      // Render fill first, then stroke on top
  strokeLinejoin: 'round',         // Round corners for consistent appearance
  strokeLinecap: 'round',          // Round line endings
  vectorEffect: 'non-scaling-stroke'  // Maintain stroke width during zoom
}}
```

**Technical Details**:

1. **strokeWidth 6**: Increased from 4 to ensure bold appearance
2. **paintOrder: 'fill stroke'**: Ensures stroke renders on top of fill, preventing overlap issues
3. **vectorEffect: 'non-scaling-stroke'**: Keeps stroke width consistent regardless of SVG viewBox scaling
4. **strokeLinejoin/strokeLinecap: 'round'**: Creates smooth, consistent corners and line endings

**Impact**:

- Orange selection border now appears consistently bold on ALL edges
- No more thin edges where counties share boundaries
- Visual consistency across different zoom levels and viewport sizes
- Professional appearance with uniform border thickness
- Better user feedback for selected/hovered states

## Technical Decisions

### Decision 1: Dual Sensor Setup vs Conditional Selection

**Context**: Desktop drag-and-drop wasn't working with conditional sensor selection

**Options Considered**:

1. **Fix conditional logic** - Pros: Simpler sensor array; Cons: Still fragile, hybrid devices problematic
2. **Use dual sensors simultaneously** - Pros: Robust, supports all inputs; Cons: Slightly more complex
3. **Separate components for mobile/desktop** - Pros: Complete separation; Cons: Code duplication, maintenance burden

**Decision**: Use dual sensor setup with both PointerSensor and TouchSensor

**Rationale**: Modern devices often support multiple input methods (Surface tablets, touchscreen laptops). Having both sensors active ensures the appropriate one activates based on the actual input method used, without requiring device detection logic that can be unreliable.

**Trade-offs**: Minimal complexity increase for maximum compatibility and robustness

---

### Decision 2: Click-to-Place vs Alternative Mobile Interactions

**Context**: Mobile users couldn't use drag-and-drop effectively

**Options Considered**:

1. **Enhanced touch sensors with better tuning** - Pros: Single interaction model; Cons: Still awkward for mobile
2. **Click-to-select + click-to-place** - Pros: Intuitive mobile UX, familiar pattern; Cons: Different from desktop
3. **Gesture-based placement (swipe, pinch)** - Pros: Novel interaction; Cons: Learning curve, accessibility issues
4. **Auto-placement mode** - Pros: Simplest; Cons: Removes puzzle challenge

**Decision**: Implement click-to-select and click-to-place pattern

**Rationale**: This is a familiar mobile interaction pattern (used in chess apps, map pins, etc.). It provides clear visual feedback (👆 indicator), works well on small screens, and doesn't require precise drag gestures that are difficult on touch devices. Desktop users can continue using drag-and-drop which is more efficient with a mouse.

**Trade-offs**: Maintains different UX patterns per platform, but optimizes each for its input method

---

### Decision 3: SVG Stroke Rendering Approach

**Context**: County borders appeared inconsistent due to SVG rendering quirks

**Options Considered**:

1. **Increase strokeWidth only** - Pros: Simple; Cons: Doesn't fix overlap issues
2. **Use outline/border CSS** - Pros: More control; Cons: Doesn't work well with SVG paths
3. **Comprehensive SVG stroke attributes** - Pros: Proper fix, professional result; Cons: More attributes to manage
4. **Separate highlight overlay** - Pros: Complete isolation; Cons: More DOM nodes, complexity

**Decision**: Use comprehensive SVG stroke attributes (paintOrder, vectorEffect, etc.)

**Rationale**: This addresses the root cause of the rendering issue rather than working around it. The SVG specification provides these attributes specifically for this use case. The solution is standards-compliant, performant, and maintainable.

**Trade-offs**: Requires understanding SVG rendering model, but provides the most robust and visually consistent result
