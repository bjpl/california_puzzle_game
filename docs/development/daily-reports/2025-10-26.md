## Technical Decisions

### Decision 1: Dual Sensor Architecture (PointerSensor + TouchSensor)

**Context**: Need drag-and-drop on desktop AND tap interactions on mobile

**Options Considered**:

1. **Conditional sensor selection** - Choose one based on device detection
2. **Dual sensors simultaneously** - Use both PointerSensor and TouchSensor
3. **Single unified sensor** - One sensor for all interactions

**Decision**: Use both sensors simultaneously with appropriate activation constraints

**Rationale**:

- @dnd-kit supports multiple sensors gracefully
- PointerSensor handles desktop mouse/trackpad
- TouchSensor handles mobile touch with delay (prevents accidental drags)
- No need for complex device detection logic
- Sensors don't conflict when properly configured

**Trade-offs**:

- Slightly more complex initialization
- Need to manage two sensor configurations
- Benefit: Robust cross-platform support without conditional logic

---

### Decision 2: TypeScript Error Resolution Strategy

**Context**: 220 TypeScript errors blocking development and pre-push hooks

**Options Considered**:

1. **Gradual fixes** - Fix errors file by file over time
2. **Comprehensive sweep** - Fix all errors in single session
3. **Type suppression** - Use @ts-ignore to bypass errors

**Decision**: Comprehensive fix in single session with type consolidation

**Rationale**:

- Created unified type system (game-types.ts) as foundation
- Fixed infrastructure (storage, sync) before application code
- Systematic approach: infrastructure → hooks → components → cleanup
- Replaced @ts-ignore with @ts-expect-error (better error visibility)
- Eliminated `any` types for actual type safety

**Trade-offs**:

- Large single commit (6,670 additions)
- Touched 62 files (merge conflict risk)
- Benefit: Clean slate, zero compilation errors, improved code quality

---

### Decision 3: Mobile Interaction Pattern (Tap vs Drag)

**Context**: Traditional drag-and-drop difficult on touch devices

**Options Considered**:

1. **Force drag on mobile** - Make users drag on touchscreens
2. **Tap-to-select, tap-to-place** - Two-step interaction
3. **Swipe gestures** - Swipe county to map location
4. **Hybrid** - Support both drag and tap

**Decision**: Tap-to-select, tap-to-place with visual feedback (plus drag support via TouchSensor)

**Rationale**:

- Tap more natural on touchscreens than drag
- Two-step interaction clearer for accuracy
- Visual feedback (selected state) shows current selection
- Still supports drag for users who prefer it (TouchSensor with delay)
- Instructions guide new users

**Trade-offs**:

- Additional component (MobileCountySelector)
- More state management (selected county)
- Benefit: Superior mobile UX, increased accessibility
